The six rules that keep it coherent 6

Every one of these is already true across all seven sheets. Breaking one is how the UI starts looking like two products.

  1. One accent, blue. Red, amber and green are reserved for state and never for decoration or branding. If a thing is not critical, warning or good, it is ink or accent.
  2. Radius encodes scale. Containers 16px, controls 10px, chips 6px, small controls 8px. A chip never gets a container's radius.
  3. Surface encodes depth. --plane is the page, --surface is a card, --surface-2 is a recess inside a card. There is no fourth level and no nested card.
  4. Numbers are tabular. Money, counts, IDs and codes all use font-variant-numeric: tabular-nums so columns align down the page.
  5. Every screen answers "what do I do now". Greeting sentence, then the KPI strip, then the blue glance tile carrying the day's actual decisions as buttons.
  6. Both themes, both languages, always. Dark mode follows the OS until the user overrides it; every user-visible string carries a Spanish twin on data-es.

What this file is, and what it is not

It is meant to be handed to whoever, or whatever, writes the next screen.

It is

  • The full stylesheet and behaviour kernel, verbatim and copyable.
  • A live specimen of every component, rendering in the real system, in both themes.
  • The page recipes and card order for all seven roles.
  • The eight-step pipeline and the cross-role handoffs written as one map.
  • A register of the data the mockups assume and an application may not have yet.

It is not

  • A component library to install. There is no build step and no dependency — it is one stylesheet and one script.
  • Permission to restyle the existing app globally. The port is screen by screen.
  • A data model. Every number in the mockups is hardcoded and every one must be replaced by a real query.
  • Final copy. The Spanish is placed, not proofed by a native ops speaker.

Icons

There is no icon library anywhere in the system — no Lucide, no Font Awesome, no SVG sprite. Every glyph is an inline Unicode character sitting in the text, inheriting its colour and size from the type around it. Correct

  • Aviso ≠ invoice — a real block on a real record.
  • installed 6, ordered 4 — a discrepancy a human must judge.
  • approved · in 9/24 run — a settled, good state.
  • A neutral fact gets the neutral chip: Guaynabo prepping.

Wrong

  • Green as a brand colour on a header or a logo.
  • Red on a destructive button that has not yet destroyed anything — the button is ghost, the resulting chip is red.
  • A fourth status colour, e.g. purple for "in transit". Use the neutral chip plus words.
  • Severity colour on a chart series. Charts use accent and accent-2.

Theming mechanics

The OS decides; the toggle overrides; the override wins for the session. Three blocks, in this order, and the order matters.

The three-block pattern
:root{ color-scheme:light; --plane:#f4f4f2; /* …light tokens… */ }

@media (prefers-color-scheme:dark){
  :root:not([data-theme="light"]){ color-scheme:dark; --plane:#0f0f0e; /* …dark… */ }
}

:root[data-theme="dark"]{ color-scheme:dark; --plane:#0f0f0e; /* …dark… */ }
The toggle
var btn = document.getElementById('themeBtn'), root = document.documentElement;
function isDark(){
  var t = root.getAttribute('data-theme');
  if (t) return t === 'dark';
  return matchMedia('(prefers-color-scheme: dark)').matches;
}
btn.addEventListener('click', function(){
  root.setAttribute('data-theme', isDark() ? 'light' : 'dark');
});
The mockups do not persist the choice. In the real application, write it to storage on click and apply it before first paint — a server-rendered page that flashes light before going dark is the one visible regression a theme port can cause.

Voice

The copy in the mockups is doing real work and is part of the specification. It has rules.

House style

  • Second person, plain verbs. "Pick up at Guaynabo", "Retake the photos Edgard sent back."
  • Name people, not roles. "Sent back by Edgard", "Dino Castillo", never "Brigade 2" or "the supervisor".
  • Sentence case everywhere, including buttons and card titles.
  • The middle dot joins facts of equal weight: run 9/10 · ACH 9/12. It is the house separator, used consistently in all seven sheets.
  • Subtitles teach the rule. "The Aviso amount must match the JAF invoice. If it doesn't, the job does not go to Finance."
  • An action keeps its name. The button says Approve, the chip says Approved, the toast says Approved.

Off style

  • Jargon from the schema: "record", "entity", "submit", "entry".
  • ALL CAPS labels, except the two places the system already uses them: photo slugs (BEFORE/AFTER) and the printed pre-cert sheet.
  • Apologies in errors. State what happened and what fixes it.
  • Empty states as mood. "Nothing here yet" is a wasted screen; say what to do.
  • Spanish as an afterthought. Every string ships with data-es at the same time it is written.

Buttons

Weight signals consequence. One primary per card; if two things look equally primary, one of them is wrong.

Signals & notifications

There is no notification bell and no notification centre anywhere in the seven sheets, and that is a deliberate design. Work announces itself where the work lives — as a count on the rail item that holds it, a chip on the row it concerns, and one sentence in the greeting. Nothing is a separate inbox to go and check.

Toast

One line, past tense, and where the work went. Try them.

Good toasts

  • "Approved. Next: Aviso & match (step 7)." — names the next step.
  • "One packet sent to Lissette. No attachments, no email." — names the person.
  • "Warehouse reconciled the return. Gate is green." — names the unlock.

Bad toasts

  • "Success!" — says nothing.
  • "Error: could not save." — a toast cannot be a failure channel; it disappears.
  • Anything with a button in it. The toast is not interactive.

Button → chip

An irreversible action does not stay clickable after it fires. The button is replaced in place by the state it produced, and a toast says where the work went. One attribute does all of it.

data-flip
<button class="btn blue"

        data-flip-es="Aprobado · factura INV-2026-0412 generada"
        data-flip-cls="ok"
        data-toast="Approved. Next: Aviso &amp; match (step 7)."
        data-toast-es="Aprobado. Siguiente: Aviso y cuadre (paso 7).">
  Approve → generate JAF invoice

In the real application the flip happens after the server confirms, and a failure restores the button and surfaces the reason in a .note.crit inside the card. The mockup flips optimistically because it has no server.

The most important signal on any sheet is one sentence of prose under the user's name, written in their terms, with the counts bolded.

Page blueprints

Two page types cover all seven sheets: the dashboard, one per role, and the task screen, one per queue or action. Everything else is a variation on those two. Assembling a new page means choosing one and filling it.

Dashboard, in order

The order is the same on all seven sheets and it encodes a reading path: who you are, how much there is, what to do now, then the detail.

  1. Greeting. Date (mobile only), "Good morning, {first name}.", and the generated sentence.
  2. KPI strip. Five tiles, or four with .kpis.k4. The last one is almost always money.
  3. Glance tile, .box.c4.acc.glance, first in the grid. Up to three decisions as buttons.
  4. Primary queue, .c8, next to it. The table of things waiting on this person, with a .split of two supporting stats beneath.
  5. Supporting panels, .c4 each. Per-person breakdown, a secondary queue, connection state.
  6. The wide chart, .c8, with the lifecycle .flow strip above it where the role owns steps.
  7. The long table, .c12, last. Everything in this role's world, with a search input in the card header.
  8. Footer. Where the numbers came from, and what is still placeholder.
The glance tile is the contract with the user: if it is empty, their day is clear. Never fill it with routine items to make it look busy.

Task screen, in order

Reached from the rail, the glance tile, or a row action. Same shell, no KPI strip.

  1. Back link. <a class="back">← Dashboard</a>, above the h1.
  2. H1 and the rule. "Step 5 of 8. The crew documented: corrected address, photos, installed per code. You approve, or send back with a note."
  3. Flow strip showing where this record sits, with .you on the steps this role owns.
  4. Record tabs if the queue has more than one, each labelled with its ID and status chip.
  5. Evidence first: address diff, photos, ordered-vs-installed, materials.
  6. Decision last, in a .c4 panel on the right: the primary action, then the note field, then the gated secondary.

Evidence left and wide, decision right and narrow. Every task screen in all seven sheets is laid out this way, which is why a supervisor can learn the warehouse screens in a minute.

Behaviour contract

The kernel is about 200 lines of plain JavaScript with no dependencies and no build step. It wires behaviour through data attributes on markup, which means server-rendered HTML gets interactivity for free and the same components work inside React, Blade, Razor or plain templates without a port.

Two rules for the port

The kernel survives a framework. Keep it that way.

  1. The router is replaceable, the rest is not. In a real app with URLs, drop data-go/data-screen and use real routes — but keep the .screen section structure, the back link and the flow strip, so a route change still looks like the mockup.
  2. Optimistic flips become confirmed flips. data-flip fires instantly because there is no server. Wire it to the response: flip on success, restore and show a .note.crit on failure. Do not leave it optimistic on anything that moves money.
Everything else — theme, language, rings, sparks, charts, toast, tabs, filter, gating, steppers, signature pads — can be lifted verbatim into any stack, because it only listens to the document.

Porting without breakage

The application already works end to end. That is an asset, not an obstacle, and the way to keep it is to move one screen at a time behind a flag, leaving the routes, the queries and the permissions exactly where they are. A visual system can be adopted without touching a single controller.

Order of operations

  1. Land the stylesheet unscoped but inert. Add the token block and the kernel CSS to the global bundle. Nothing changes yet, because no existing markup uses .box, .kpi or .rail. If it does, rename the system's classes with a prefix before you go further — that collision check is the whole risk of step 1.
  2. Replace the shell. Rail, top bar, wrap, footer. The shell is the loudest 80% of the impression and touches no business logic.
  3. Port one dashboard. Pick the role with the least logic. Build the greeting, the five KPIs and the glance tile against real queries. Ship it behind a per-user flag.
  4. Port that role's task screens next, so one person's whole day is consistent. A half-ported role is worse than an unported one.
  5. Repeat per role. Supervisor, warehouse, crew, Lissette, Carmen, installer, Monica.
  6. Close the gaps last. The new fields in the register are additive; the UI can ship with a card that honestly says the data is not wired yet.
Do not begin with a global find-and-replace of the old stylesheet. That is the one approach that guarantees a regression in a screen nobody remembered existed.

Collision check, first

The system uses short, generic class names — .box, .top, .grid, .tag, .inp, .chk, .flow, .rows, .split, .stat, .note, .more, .back, .sm, .num, .act. Grep the existing app for each before you add anything.

If they are free

  • Ship the kernel as-is. Every snippet in this file then works unedited.

If any collide

  • Prefix the system, not the app: .jaf-box, .jaf-tag. Do it with one scripted rename so this guide stays the source of truth.
  • Or scope the whole system under a wrapper class and render ported screens inside it.

Do not solve a collision with !important or by raising specificity. The kernel's selectors are deliberately flat and a specificity war will surface later as a broken dark mode.

What must not change

  • ✕Route names, URLs and deep linkskeep
  • ✕Permissions, roles and row-level visibilitykeep
  • ✕Existing queries, jobs and integrationskeep
  • ✕Record identifiers and numbering schemeskeep
  • ✕Anything currently posting to an external systemkeep

The port is a presentation change. If a pull request touches both a template and a migration, split it.

Missing primitives

Three things the seven mockups do not have, which a production system needs and which this guide's own acceptance checklist assumes. I am naming them rather than letting them be inherited silently — and supplying the code, because each is small and each is the kind of thing that never gets added later.

1 · Keyboard access and focus

The kernel defines exactly one focus style, .inp:focus. Everything else relies on the browser default, and several controls are not reachable by keyboard at all because they are div and span elements with click handlers.

ControlElement in the mockupsProblem
Checkbox<span class="chk">Not focusable, not operable by keyboard, no announced state
Signature pad<div class="sigpad">Not focusable. Gates a release.
Crew option<div class="crewopt">Not focusable, no group semantics
Catalog option<div class="opt">Not focusable inside a search result list
Quantity stepper<span>−</span>Not focusable; the value is a <b>, not an input
Radio<label class="on">No underlying input, so no group or arrow-key behaviour
Warehouse and crew staff count stock at a counter and sign for it. If the checkbox and the signature pad are mouse-only, the two screens that move physical inventory are the least accessible in the product.

The fix, in two parts

First, give every interactive thing a visible ring in the system's own accent. Second, build them from real elements — <button type="button"> with aria-pressed for the checkbox and crew option, a real <input type="radio"> behind the radio label, and a real number input inside the stepper. The CSS below assumes that change and costs nothing if you make it.

  outline: none;
  box-shadow: 0 0 0 3px var(--accent-wash), 0 0 0 1px var(--accent);

}

3 · Empty states

Every list, table and queue in the mockups is populated, because they are demonstrations. Not one empty state exists — and the roles most likely to see one are the field roles, on a good day.

Nothing waiting on you.
Your four brigades have 8 jobs open and none of them need a decision yet.

Rules

  • Say what is true, not what is absent
    "Nothing waiting on you", not "No results found"
  • Then say what the person could do
    one ghost button, never a primary
  • A cleared queue is good news
    it reads as reassurance, not as an error
  • A filtered-to-nothing table is different
    offer to clear the filter, not to create a record

The glance tile is the one place that already handles emptiness well by design: if it has no buttons, the day is clear. Match its tone.
